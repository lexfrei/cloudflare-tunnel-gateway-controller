# GatewayClass SHOULD / MAY assessment (GC-*)

Architecture: GatewayClass is bound by `spec.controllerName`; the status-only `GatewayClassReconciler` (`internal/controller/gatewayclass_controller.go`) writes the `Accepted` and `SupportedVersion` conditions. The Cloudflare credentials / tunnelID come from a `GatewayClassConfig` resolved via `parametersRef` by `internal/config/resolver.go`. Verdicts below were re-derived from the live code, not from `rows-GC.md`.

## SHOULD clauses

| ID | Keyword | Verdict | Evidence | Notes |
| --- | --- | --- | --- | --- |
| GC-02 | SHOULD | HONOURED-TESTED | gatewayclass_controller.go reconcileFinalizer + Gateway watch; tests gatewayclass_finalizer_test.go | The reconciler now adds `gateway-exists-finalizer.gateway.networking.k8s.io` while any Gateway uses the class and removes it when none do (never added to a deleting class; removal unblocks deletion). Documented in limitations.md ("The gateway-exists finalizer is managed"). |
| GC-05 | SHOULD | HONOURED-TESTED | gatewayclass_controller.go parametersRefProblem, gatewayClassesForConfig; tests in gatewayclass_controller_test.go (`TestGatewayClassReconciler_SetAcceptedConditions_InvalidParametersRef`, `TestGatewayClassReconciler_ConfigCreatedLater_AcceptsClass`, `TestGatewayClassReconciler_ConfigDeleted_RefusesClass`) | `setAcceptedConditions` reports GatewayClass Accepted=False/InvalidParameters for a missing `parametersRef`, an unsupported group or kind, a namespace on the ref, or a GatewayClassConfig that does not exist, with a message naming the problem. Creating or deleting the config re-evaluates the class through a GatewayClassConfig watch. Malformed config data is rejected at admission by the CRD schema. |
| GC-10 | SHOULD | HONOURED-TESTED | gatewayclass_controller.go parametersRefProblem; test TestGatewayClassReconciler_SetAcceptedConditions_InvalidParametersRef | Accepted=False carries Reason=InvalidParameters and a Message naming the specific `parametersRef` problem; the table test asserts the reason and the message for each case. |
| GC-15 | SHOULD | HONOURED-TESTED | gatewayclass_controller.go `bundleVersionSupported` (message names installed bundle AND `controller requires %d.%d.x`); tests in gatewayclass_controller_test.go (see Notes) | UnsupportedVersion message includes both the detected CRD version (`installed`) and the controller's required major.minor. Still HONOURED-TESTED (the condition is exercised), with a partial-assertion note. |

## MAY clauses

| ID | Verdict | Evidence | Notes |
| --- | --- | --- | --- |
| GC-13 | OMITTED-INTENTIONAL | gatewayclass_controller.go `bundleVersionCondition` | Best-effort support for an unrecognised CRD version. The controller does NOT pursue this option: on any major.minor skew it deterministically reports SupportedVersion=False/UnsupportedVersion rather than attempting partial support. It does, however, leave Accepted=True (does not hard-reject), so it neither claims best-effort support (GC-13) nor refuses outright (GC-14) — it signals skew and keeps running. Choosing not to provide best-effort support is a valid MAY stance. |
| GC-14 | OMITTED-INTENTIONAL | gatewayclass_controller.go `setAcceptedConditions` | The alternative "refuse to support unrecognised CRD versions" is also not taken in the strong sense: Accepted stays True even on an unsupported bundle, so Gateways are still provisioned. The controller's actual posture is "warn via SupportedVersion=False, keep serving" — neither MAY option is selected as written; the SHOULD signal (GC-15) carries the operator warning instead. Valid: both GC-13 and GC-14 are MAY, so declining both is conformant. |
